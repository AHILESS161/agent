# Production-архитектура «Регистра»

**Статус:** инфраструктура подготовлена, покупка сервера отложена.
**Актуально:** 26 августа 2026 года.

## Решение

На первом коммерческом этапе используется один VPS в российском дата-центре,
но приложение не зависит от конкретного провайдера. В репозитории разделены:

- локальный контур: `docker-compose.yml`, SQLite и Vite dev server;
- production-контур: `docker-compose.prod.yml`, PostgreSQL, статический frontend,
  HTTPS и постоянные тома;
- CI: `.github/workflows/ci.yml`, проверяющий backend, frontend и оба образа;
- операции: `deploy/deploy.sh` и `deploy/backup.sh`.

## Схема компонентов

```text
Интернет
   │  HTTPS :443
   ▼
Caddy ── автоматический TLS и security headers
   │
   ▼
Nginx frontend ── React SPA
   │ /api/*
   ▼
FastAPI
   ├── PostgreSQL 16       — пользователи, заявки, аудит и результаты
   ├── documents volume    — оригиналы и изображения по SHA-256
   ├── внешний LLM API     — только необходимый контекст анализа
   └── Роспатент           — read-only поиск
```

Наружу публикуются только `80/443`. PostgreSQL и FastAPI находятся во внутренней
Docker-сети. SSH ограничивается файрволом сервера и ключевой аутентификацией.

## Что уже обеспечено

- production-образы запускаются без root;
- `.dockerignore` исключает `.env`, базы, документы, тестовые файлы и логи;
- схема PostgreSQL изменяется только Alembic-миграциями;
- API имеет отдельные `/health` и `/ready`;
- API-документацию можно выключить через `API_DOCS_ENABLED=false`;
- `TrustedHostMiddleware` ограничивает допустимые домены;
- frontend собирается один раз и раздаётся Nginx, Vite на сервере не работает;
- Caddy автоматически получает и обновляет TLS-сертификат;
- документы и PostgreSQL лежат в разных постоянных Docker volumes;
- создание первого администратора не требует demo-пользователей;
- CI не использует реальные LLM/FIPS-ключи.

## Первый запуск

Требования к чистому Ubuntu 24.04: Git, Docker Engine и Docker Compose plugin.

```bash
git clone https://github.com/AHILESS161/agent.git registr
cd registr
git checkout main
cp .env.production.example .env.production
chmod 600 .env.production
# заполнить DOMAIN, POSTGRES_PASSWORD, DATABASE_URL, SECRET_KEY и ключ выбранной LLM

docker compose --env-file .env.production -f docker-compose.prod.yml build
docker compose --env-file .env.production -f docker-compose.prod.yml up -d postgres
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm migrate
docker compose --env-file .env.production -f docker-compose.prod.yml up -d
```

Перед запуском DNS-запись `A` домена должна указывать на IPv4 сервера, а порты
80 и 443 должны быть открыты. PostgreSQL наружу не публикуется.

Первый администратор создаётся интерактивно, пароль не остаётся в shell history:

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml run --rm -it \
  api python scripts/create_admin.py --email admin@example.ru --name "Администратор"
```

Demo seed в production запускать запрещено.

## Обновление

```bash
./deploy/deploy.sh
```

Порядок намеренно фиксирован: fast-forward обновление кода, сборка образов,
запуск PostgreSQL, миграция, затем перезапуск приложения. При ошибке миграции
новая версия API не поднимается автоматически.

После появления постоянного сервера следующий PR добавит CD: GitHub Actions
будет подключаться по SSH только после успешного CI и merge в `main`. До выдачи
адреса сервера, пользователя и SSH host key добавлять фиктивный deploy job нельзя.

## Резервное копирование

`deploy/backup.sh` создаёт согласованный логический дамп PostgreSQL и архив
документов. На сервере его следует запускать ежедневно через `systemd timer` или
cron. Локально сохраняются семь последних комплектов.

Это не завершённая стратегия, пока копии остаются на том же VPS. До приёма
реальных паспортов необходима вторая, зашифрованная копия в S3 российского
региона и ежемесячная проверка восстановления на отдельной базе.

Восстановление выполняется только по отдельной инструкции после проверки хэшей:

1. остановить `api` и `web`;
2. создать пустую PostgreSQL;
3. применить `pg_restore --clean --if-exists` к выбранному дампу;
4. восстановить архив документов в `registr_documents_data`;
5. выполнить `/ready` и выборочно скачать несколько документов;
6. записать результат проверки восстановления.

## Секреты и персональные данные

- `.env.production` никогда не передаётся в Git;
- все ключи, когда-либо отправленные в чат или сообщение, необходимо отозвать;
  это относится в том числе к ранее опубликованным ключам GigaChat и RouterAI;
- JWT secret и пароль PostgreSQL генерируются случайно и не повторяются;
- во внешнюю LLM не передаются паспорта, адреса и реквизиты, если они не нужны
  конкретному анализу;
- сервер, основная база, документы и резервные копии размещаются в России;
- доступ к документам предоставляется только через авторизованный API;
- до коммерческого запуска оформляются политика обработки данных, согласие,
  поручение обработчикам и уведомление Роскомнадзора, если оно требуется.

## Что сознательно отложено

Пороговые нагрузки, стоимость CPU/GPU-контуров и условия перехода к SLA 99,9%
описаны в [`operating-economics-and-sla.md`](operating-economics-and-sla.md).

Для пилота не добавляются Kubernetes, несколько backend-реплик и отдельная
очередь: они увеличат стоимость и количество точек отказа без текущей нагрузки.

Перед масштабированием понадобятся:

1. S3-адаптер вместо локального document volume;
2. очередь для OCR и полного анализа;
3. Redis rate limiting для нескольких API-процессов;
4. управляемый PostgreSQL с point-in-time recovery;
5. метрики, централизованные логи и оповещения;
6. два экземпляра приложения и балансировщик.

Такая граница позволяет начать на одном VPS без архитектурного тупика: база,
файлы и HTTP-приложение уже разделены и могут переноситься независимо.
