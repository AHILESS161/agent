# Архитектура системы автоматизации регистрации товарных знаков

> **Версия:** 1.0  
> **Дата:** 2026-03-29  
> **Статус:** MVP+ (базовая версия с полным агентным конвейером)

---

## 1. Обзор системы

### 1.1 Назначение

Система автоматизирует рабочий процесс регистрации товарных знаков для российской юридической фирмы. Она охватывает полный жизненный цикл заявки — от первичного приёма данных клиента до подачи документов в ФИПС (Федеральный институт промышленной собственности) и мониторинга статуса.

Ключевые задачи:
- **Сокращение ручного труда** юристов за счёт автоматической первичной проверки, классификации по МКТУ и поиска конфликтов.
- **Обеспечение аудируемости** каждого шага в соответствии с требованиями ГК РФ, часть IV.
- **Человек в контуре (HITL)** — система консультирует, а не решает; финальные правовые суждения всегда за юристом.
- **Масштабируемость** за счёт модульной архитектуры с чёткими границами контекстов.

### 1.2 Область применения

| Параметр | Значение |
|---|---|
| Юрисдикция | Российская Федерация (ГК РФ, часть IV) |
| Тип клиентов | Один арендатор — одна юридическая фирма |
| Объект регистрации | Товарные знаки (словесные, изобразительные, комбинированные) |
| Орган подачи | ФИПС / Роспатент |
| Классификация | МКТУ (Международная классификация товаров и услуг), ред. 12 |
| Язык системы | Русский (пользовательский интерфейс и документы), English (код) |

## 3. Модульный монолит: 18 ограниченных контекстов

Система построена как **модульный монолит** (Modular Monolith) — единый развёртываемый артефакт с жёсткими внутренними границами. Границы контекстов (Bounded Contexts) соблюдаются через импорты только из публичных API модулей (`__init__.py`), без прямого доступа к внутренним модулям.

### 3.1 Карта контекстов

```
backend/
├── app/
│   ├── auth/           # Аутентификация и сессии (JWT, refresh tokens)
│   ├── users/          # Системные пользователи (юристы, менеджеры, admin)
│   ├── clients/        # Клиенты фирмы и их представители
│   ├── applications/   # Заявки на регистрацию ТЗ (основной агрегат)
│   ├── intake/         # Первичный приём и валидация данных
│   ├── legal_review/   # Правовая экспертиза (абсолютные и относительные основания)
│   ├── classification/ # МКТУ-классификация
│   ├── conflict_search/# Поиск конфликтующих обозначений
│   ├── documents/      # Шаблоны документов и сборка пакетов
│   ├── submission/     # Подача в ФИПС и квитанции
│   ├── status_tracking/# Мониторинг статуса после подачи
│   ├── notifications/  # Email / Telegram уведомления
│   ├── prompts/        # Реестр промптов и их версионирование
│   ├── llm/            # Абстракция над LLM-провайдерами
│   ├── rag/            # RAG-конвейер (ingestion, retrieval)
│   ├── audit/          # Журнал аудита всех значимых событий
│   ├── admin/          # Административный интерфейс (промпты, модели, задания)
│   └── integrations/   # Адаптеры внешних сервисов (ФИПС, S3, etc.)
```

### 3.2 Описание контекстов

| Контекст | Ответственность | Ключевые агрегаты |
|---|---|---|
| **auth** | JWT-аутентификация, управление сессиями, refresh-токены | `Session`, `RefreshToken` |
| **users** | CRUD пользователей, роли, права доступа | `User`, `Role` |
| **clients** | Клиентские данные, представители, доверенности | `Client`, `ClientRepresentative` |
| **applications** | Жизненный цикл заявки, оркестрация состояний | `TrademarkApplicationDraft` |
| **intake** | Первичная валидация, нормализация, запрос недостающих данных | `IntakeValidationResult` |
| **legal_review** | Правовая экспертиза по ст. 1483 ГК РФ | `LegalReview`, `LegalFinding` |
| **classification** | Предложение классов МКТУ, уточнение перечня | `NiceClassSuggestion` |
| **conflict_search** | Поиск конфликтующих ТЗ в базе ФИПС | `ConflictSearchJob`, `ConflictSearchResult` |
| **documents** | Сборка DOCX-пакета, шаблоны | `DocumentTemplate`, `DocumentPackage` |
| **submission** | Отправка в ФИПС, хранение квитанций | `Submission` |

| **integrations** | Адаптеры: ФИПС API, S3, SMTP | — |

## 4. Чистая архитектура (Clean Architecture)

Каждый контекст следует слоистой структуре:

```
context/
├── api/            # FastAPI router — только HTTP-преобразование
│   ├── router.py
│   └── schemas.py  # Pydantic v2 input/output schemas
├── services/       # Бизнес-логика, оркестрация use-cases
│   └── service.py
├── domain/         # Чистые доменные объекты, правила, события
│   ├── models.py   # SQLAlchemy ORM models
│   ├── entities.py # Pydantic domain entities (без ORM)
│   └── events.py   # Domain events
├── infrastructure/ # Реализации портов: репозитории, клиенты
│   ├── repository.py
│   └── adapters.py
└── __init__.py     # Публичный API контекста
```

**Правило зависимостей:** внешние слои зависят от внутренних; domain не импортирует ничего из api/infrastructure.

## 6. Ключевые архитектурные решения (ADR)

### ADR-001: Модульный монолит вместо микросервисов

**Статус:** Принято  
**Контекст:** MVP для одной фирмы, небольшая команда разработки.  
**Решение:** Единый развёртываемый артефакт с границами контекстов через Python-пакеты.  
**Последствия:** Упрощает разработку и отладку; при необходимости модули извлекаются в сервисы.

### ADR-002: SQLite → PostgreSQL миграция

**Статус:** Принято  
**Контекст:** SQLite достаточен для разработки и раннего продакшена (< 5 одновременных пользователей).  
**Решение:** SQLAlchemy async с dialect-агностичными запросами; Alembic-миграции работают для обеих БД.  
**Триггер перехода:** > 10 одновременных пользователей или необходимость pgvector.

### ADR-003: LLM-агностичный провайдер

**Статус:** Принято  
**Решение:** Абстракция через LangChain `BaseChatModel`. Конфигурация провайдера через переменные среды. Переключение модели без изменения кода агентов.

### ADR-004: ФИПС через mock-провайдер

**Статус:** Принято  
**Контекст:** Реальный API ФИПС не предоставляет тестовую среду; публичного REST API нет.  
**Решение:** Интерфейс `FIPSProvider` с двумя реализациями: `MockFIPSProvider` и `RealFIPSProvider`. Переключение через конфигурацию.

### ADR-005: Человек в контуре (HITL)

**Статус:** Принято  
**Решение:** LangGraph `interrupt_before` на 4 узлах. Юрист подтверждает переход — без его действия автоматика не продолжается.

## 7. Контрольные точки HITL (Human-in-the-Loop)

| № | Точка | Триггер | Действие юриста |
|---|---|---|---|
| 1 | **Правовая экспертиза** | Завершение агентов AbsoluteGrounds + RelativeGrounds | Подтверждение/корректировка выводов экспертизы |
| 2 | **Классы МКТУ** | Предложения NiceClassification агента | Утверждение или изменение перечня классов |
| 3 | **Рекомендация** | Готовность RecommendationMemo | Согласование или отклонение рекомендации |
| 4 | **Пакет документов** | Сборка DocumentPackage завершена | Финальное подписание и одобрение перед подачей |

## 8. Ключевые допущения

1. **ФИПС API** — интеграция через mock-провайдер; реальный API подключается без изменения бизнес-логики.
2. **LLM-агностичность** — по умолчанию `huihui_ai/qwen2.5-abliterate:14b` через Ollama; провайдер меняется в конфигурации.
3. **RAG-база** — инициально засеивается публичными правовыми текстами (ГК РФ ч. IV, руководства Роспатента); коммерческие правовые БД подключаются позднее.
4. **Один арендатор** — система не является multi-tenant; вся изоляция на уровне RBAC.
5. **Юрисдикция** — только РФ; международные заявки (Мадридская система) вне области применения MVP+.
6. **HITL обязателен** — автоматическая подача без одобрения юриста технически невозможна.

## 9. Ключевые риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Галлюцинации LLM в правовом контексте | Высокая | Критическое | HITL на всех ключевых шагах; structured output only; RAG с цитированием |
| Нестабильность ФИПС API | Высокая | Высокое | Mock-провайдер; retry с exponential backoff; очередь заданий |
| Качество RAG-базы знаний | Средняя | Высокое | Версионирование источников; confidence threshold; fallback-режим |
| Утечка персональных данных клиентов | Низкая | Критическое | PII masking в логах; шифрование at-rest; минимальный доступ |
| Изменение законодательства | Средняя | Высокое | Промпты и RAG-база обновляются независимо от кода |

## 10. Нефункциональные требования

| Требование | Цель |
|---|---|
| **Аудируемость** | Каждое значимое действие записывается в `AuditLog` с пользователем, временем, until и after состоянием |
| **RBAC** | Четыре роли: `admin`, `lawyer`, `manager`, `client`; права на уровне эндпоинта и поля |
| **Структурированные выходы** | Все LLM-ответы — через Pydantic-схемы; free-text ответы запрещены в бизнес-логике |
| **Производительность** | API P95 < 300 мс (без LLM-вызовов); LLM-запросы — асинхронно |
| **Доступность** | 99.5% uptime (нет требований к HA на MVP+) |
| **Резервное копирование** | Ежедневный snapshot БД; файлы в S3 с версионированием |
| **Локализация** | Все пользовательские тексты и документы — на русском языке |
