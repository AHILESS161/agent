# Персональные данные: фактическая модель угроз и правила обработки

**Актуализировано:** 28 августа 2026 года.  
**Статус:** технический baseline текущего MVP, а не заключение о соответствии
152-ФЗ и не готовый локальный акт оператора.

Документ отвечает на три вопроса: какие сведения получает «Регистр», куда они
попадают и что необходимо сделать до работы с реальными клиентами. Общий
целевой дизайн безопасности находится в [`security.md`](security.md), а здесь
описано только фактически реализованное и явно оставшиеся решения.

## Какие данные обрабатываются

| Объект | Данные | Для чего нужны |
|---|---|---|
| Учётная запись | имя, e-mail, телефон, роль | вход, связь и разграничение доступа |
| Заявитель | ФИО/наименование, адрес, страна, ИНН, ОГРН/ОГРНИП, КПП | заполнение заявления и проверка комплектности |
| Подписант и представитель | ФИО, должность, реквизиты представительства | определение лица, которое вправе действовать по заявке |
| Материалы дела | выписки ЕГРЮЛ/ЕГРИП, доверенности, уведомления, доказательства, при необходимости паспорт | извлечение и подтверждение только необходимых для заявления фактов |
| Обозначение | текст, изображение, аудиозапись, описание, товары и услуги | классификация, поиск и правовой анализ |
| Журнал действий | пользователь, дело, тип действия, время, IP и технические метаданные | расследование ошибок и подтверждение юридически значимых действий |

Паспорт не является обязательным документом по умолчанию и не попадает в ZIP
для подачи. Если для конкретного заявителя он действительно нужен, продукт
должен извлекать только поля, требуемые официальной формой, а не создавать
постоянный архив копий паспортов.

## Потоки и границы доверия

1. Браузер передаёт сведения в API после авторизации.
2. Структурированные поля сохраняются в базе, оригиналы документов — в
   локальном файловом хранилище с адресацией по SHA-256.
3. Извлечение текста, OCR выписок и формирование DOCX выполняются локально.
4. Во внешнюю текстовую модель для классов и правовой проверки передаются
   обозначение, его описание, выбранные товары/услуги, классы МКТУ и нужные
   фрагменты правовой базы. Имя заявителя, адрес, ИНН, паспорт, доверенность и
   данные подписанта для такой оценки не нужны и не передаются.
5. Для анализа изображения внешней мультимодальной моделью передаётся само
   изображение знака. Пользователь должен видеть это до запуска операции.
6. Разбор заполненного бланка через LLM является отдельным необязательным
   режимом `use_llm`; по умолчанию он выключен. До production его нельзя
   включать без понятного уведомления пользователю, основания обработки и
   договора с провайдером. Обычный разбор выполняется локальными правилами.

## Основные угрозы и действующие меры

| Угроза | Что сделано сейчас | Остаточный риск |
|---|---|---|
| Пользователь подбирает ID чужого дела или документа | чтение, загрузка, извлечение, подтверждение и удаление сверяют владельца/назначенного сотрудника; администратор имеет общий доступ | матрицу доступа необходимо регулярно проверять API-тестами |
| Юрист видит общий журнал компании | журнал юриста ограничен созданными и назначенными ему делами; общий журнал доступен администратору | события без связи с делом видит только администратор |
| Клиент читает представителей другого заявителя | карточка заявителя проверяется перед чтением и добавлением представителя | сотрудники пока видят общий справочник клиентов — это осознанная модель организации, которую надо подтвердить до пилота |
| Удалена запись, но исходный файл остался на диске | удаление документа и черновой заявки освобождает физический blob; общий blob удаляется только после исчезновения последней ссылки | резервные копии должны иметь отдельный ограниченный срок жизни |
| Случайно удалены материалы поданного дела | отдельный документ нельзя удалить у поданной/закрытой заявки или пока он связан с ответом Роспатенту | удаление по требованию субъекта в таком деле требует отдельного решения оператора с учётом обязательных сроков хранения |
| PII размножается в журнале | изменения фиксируются как перечень полей без копии ФИО, адреса, контактов, подписанта и имени файла; чувствительные извлечённые значения маскируются | старые записи тестовой/локальной БД не очищаются автоматически |
| PII попадает во внешний LLM | основной анализ использует минимальный предметный контекст; имя заявителя удалено и из старого recommendation-пайплайна | необязательный LLM-разбор бланка и vision требуют отдельного прозрачного согласования |
| Утечка диска или backup | production-архитектура требует размещение в РФ, TLS, шифрование диска/объектного хранилища и зашифрованную внешнюю копию | локальный MVP не шифрует БД и каталог файлов на уровне приложения |

## Правила хранения и удаления

152-ФЗ не устанавливает универсальное правило «хранить всё пять лет».
Персональные данные должны храниться не дольше, чем этого требует цель
обработки, а после достижения цели — уничтожаться или обезличиваться, если иной
срок не установлен законом или договором. Поэтому до пилота оператор должен
утвердить локальный акт со сроком для каждой категории, а не один срок на все
данные.

Технически сейчас действует следующее:

- черновую заявку до подачи можно удалить вместе с её строками БД и исходными
  файлами;
- отдельный исходный документ черновика можно удалить через API; извлечённые
  страницы, поля и подтверждения удаляются каскадно;
- поданная и закрытая заявка защищены от обычного удаления;
- паспорт не включается в пакет подачи;
- автоматического удаления по возрасту и удаления из backup пока нет.

До внешнего пилота необходимо письменно утвердить минимум четыре срока:

1. срок жизни незавершённого и неактивного черновика;
2. момент удаления оригинала паспорта после подтверждения необходимых полей;
3. срок хранения материалов завершённого поручения и отдельно журнала действий;
4. срок жизни резервных копий и максимальную задержку удаления данных из них.

Конкретные числа здесь намеренно не придуманы: они зависят от договора с
клиентом, фактической цели обработки, требований к бухгалтерским и юридическим
документам и выбранной схемы сопровождения после подачи.

## Что обязательно до реальных клиентов

- назначить оператора персональных данных и владельца процесса удаления;
- составить перечень целей, категорий данных, субъектов, получателей и
  операций; проверить обязанность уведомления Роскомнадзора;
- оформить согласия/иные основания обработки и поручение обработки внешним
  LLM-провайдерам; отдельно описать передачу изображения;
- разместить базы граждан РФ и документы в российской инфраструктуре;
- включить TLS, шифрование диска/объектного хранилища, secret store,
  зашифрованные backup и проверку восстановления;
- утвердить сроки выше, реализовать планировщик удаления и журнал результата
  уничтожения;
- провести проверку прав доступа и тестовое удаление по каждому виду документа.
