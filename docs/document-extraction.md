# Обработка документов и извлечение данных

> **Актуализировано 26.08.2026:** поддержаны текстовые PDF, DOCX/TXT и OCR для
> PDF/PNG/JPG. Код страны, контакты и сведения об обозначении также переносятся
> в рабочий черновик; источник и необходимость ручного заполнения показываются
> пользователю.

Как система превращает загруженный файл в проверяемые реквизиты.

**Главный принцип:** извлечение детерминированное. Regex и правила, без LLM.
На приложенной к репозиторию выписке ЕГРЮЛ это даёт **21 из 21 поля**.

---

## 1. Приложенные документы

| | Выписка ЕГРЮЛ | Пример заявки |
|---|---|---|
| Путь | `Выписка_ЕГРЮЛ_03062020-1.pdf` | `Пример заявки.pdf` |
| SHA-256 | `10062fbf4e570fd0d4342a0992a4f645aefe0c3139ea926c1ef3cafa8180df7e` | `c92c0cc0bd4b86409f234c09067de7a367a41d551b3d326cb2ed14de77c10ed6` |
| Размер | 171 095 Б | 544 201 Б |
| Формат | PDF 1.4, 10 страниц | PDF 1.5, 3 страницы |
| Текстовый слой | есть (15 951 симв.) | есть (9 840 симв.) |
| OCR требуется | нет | нет |
| Фактический тип | `egrul_extract` | заполненный бланк Роспатента |

Оригиналы не изменяются: открываются только на чтение.

> **Уточнение по постановке задачи.** Справка была обозначена как «ЕГРН».
> По содержимому это **выписка ЕГРЮЛ**: ОГРН, ИНН, КПП, наименование,
> руководитель, ОКВЭД. Сведений об объектах недвижимости в ней нет.
> Обрабатывается как `egrul_extract`.

## 2. Пайплайн

```
файл → проверка → хранилище → постраничный текст → тип документа
     → извлечение полей (regex) → валидация → кандидаты
     → сверка с полями дела и заявления → подтверждение специалистом
```

### 2.1 Проверка и хранение

`app/services/file_storage.py`

Поддерживаются PDF, DOCX, TXT, PNG, JPG/JPEG. Тип определяется **по
сигнатуре содержимого**, а не по расширению и не по заявленному
`Content-Type`: иначе достаточно переименовать исполняемый файл в `.pdf`.

Расхождение расширения и содержимого — отказ. DOCX отличается от обычного
ZIP по наличию `word/` внутри. Для TXT дополнительно отсекается содержимое
с нулевыми и управляющими байтами: CP1251 декодирует почти любые байты,
и без этой проверки бинарник проходил как текст.

Файлы адресуются по SHA-256 с двухуровневым шардингом. Повторная загрузка
того же содержимого не создаёт копию. Имя файла на путь не влияет —
path traversal невозможен.

Прямых ссылок на хранилище нет: скачивание идёт через
`GET /source-documents/{id}/download` с проверкой авторизации.

### 2.2 Извлечение текста

`app/services/document_text_extractor.py` — `extract_pages_from_bytes()`

Постранично, с фиксацией способа: `pdf_text_layer`, `docx_parser`,
`plain_text`, `ocr`. Каждое извлечённое поле ссылается на конкретную страницу.

`ocr_confidence` заполняется **только при OCR**; для текстового слоя
остаётся `NULL`, чтобы отсутствие OCR не выглядело как стопроцентная
уверенность.

Для PDF применяется гибридная схема: сначала читается текстовый слой, а для
пустых или почти пустых страниц автоматически запускается Tesseract OCR.
PNG и JPG/JPEG распознаются целиком. Поддерживаются русский и английский
языки; средняя уверенность Tesseract сохраняется на уровне страницы.

Порог включения OCR и параметры распознавания задаются через
`OCR_MIN_TEXT_CHARS`, `OCR_DPI`, `OCR_LANGUAGES`, `OCR_PSM` и
`OCR_TIMEOUT_SECONDS`. В Docker движок Tesseract и языковые пакеты `rus` и
`eng` устанавливаются автоматически. При локальном запуске Windows нужно
установить Tesseract 5 и при необходимости указать полный путь в
`OCR_TESSERACT_CMD`. Нестандартную папку языковых моделей можно задать через
`OCR_TESSDATA_DIR`.

Если распознавание пустой страницы невозможно, система возвращает понятную
ошибку и сохраняет оригинал. Для короткой страницы, где текстовый слой всё же
есть, сбой OCR не уничтожает уже извлечённый текст.

### 2.3 Изображение товарного знака

Для обозначения используется отдельный маршрут, а не общая карточка документа:

1. `POST /applications/{id}/mark-image` принимает только настоящий PNG/JPEG;
2. Pillow проверяет декодирование и ограничение по числу пикселей;
3. сохраняются размер, формат, цветовая модель, основные цвета и `dHash`;
4. Tesseract предлагает словесные элементы, но пользователь подтверждает или
   исправляет их в поле «Слова на логотипе»;
5. `GET .../content` отдаёт защищённое превью с той же проверкой доступа;
6. замена/удаление меняет активную связь, сохраняя предыдущую запись для аудита.

Отсутствие текста не является ошибкой для изобразительного знака. OCR помогает
текстовому поиску комбинированных обозначений, но не заменяет сравнение графики.

### 2.4 Определение типа

`app/document_processing/classifier.py`

По устойчивым заголовкам и обязательным реквизитам. Возвращает тип,
уверенность и список сработавших маркеров — решение объяснимо.

Если заголовок не опознан, но реестровые реквизиты присутствуют, документ
помечается `unknown_registry_extract`. **Тип документа всегда требует
подтверждения специалистом**, независимо от уверенности: цена ошибки —
реквизиты из непрофильного документа в заявлении.

## 3. Извлечение полей

`app/document_processing/extractors/registry.py`
Паттерны: `app/document_processing/patterns/egrul.yaml` и `egrip.yaml`
(версионируются отдельно от кода).

### 3.1 Почему все паттерны привязаны к подписи поля

«Голый» поиск цифр в типовой выписке даёт ложные срабатывания. Проверено
на приложенном документе:

| Ловушка | Что мешает | Решение |
|---|---|---|
| ОГРН | ≥6 номеров ГРН той же длины (13 цифр) | якорь на подпись `ОГРН` + контрольная сумма |
| ИНН организации | ещё 4 ИНН: руководитель + 3 учредителя | строго 10 цифр (у физлиц 12) |
| ФИО руководителя | те же подписи у учредителей | разбор по **разделам** документа |
| Дата регистрации | встречается 3 раза: ЮЛ, ПФР, ФСС | раздел `Сведения о регистрации` |
| ОГРН вразрядку | на титульном листе `1 1 8 4 2 …` | нормализатор `digits` |
| Колонтитул | вклинивается посреди таблицы | терминатор `{ROW_END}` |

### 3.2 Валидация

`app/document_processing/validators.py`

Контрольные суммы ИНН (10/12), ОГРН (13), ОГРНИП (15), структура КПП,
разумность дат. Проверки длины недостаточно — она не отличает ОГРН от
номера ГРН.

> Реквизиты в **образце заявки** синтетические и контрольные суммы не
> проходят (ИНН `7736777555`, ОГРН `1037746123123`). Это ожидаемо: они
> должны вести к `needs_review`, а не приниматься молча и не отбрасываться.

### 3.3 Кандидаты и конфликты

| Ситуация | Статус | Поведение |
|---|---|---|
| Одно значение, валидация пройдена | `matched` | — |
| Одно значение из нескольких паттернов | `matched` | подтверждение: уверенность растёт, но **никогда не достигает 1.0** |
| Разные значения | `conflict` | сохраняются **все** кандидаты, выбирает специалист |
| Валидация не пройдена | `needs_review` | указывается причина |
| Обязательное не найдено | `missing` | — |

Молча брать первый вариант запрещено.

### 3.4 Нормализация

`app/document_processing/normalizers.py`

Никогда не молчаливая: хранятся исходное и приведённое значение плюс факт
изменения. Специалист видит, что именно система изменила.

Адрес собирается из компонентов таблицы (индекс, регион, город, улица,
дом, офис). Собранное значение **всегда** требует проверки: порядок и
состав частей задаются правилом, а не прочитаны целиком.

### 3.5 Перенос ЕГРЮЛ и ЕГРИП в заявку

После загрузки выписки извлечённые значения сохраняются в карточке заявителя,
а не живут только в ответе загрузки. Повторное открытие экрана восстанавливает
их из сохранённого результата разбора.

- ЕГРЮЛ переносит наименование, ИНН, ОГРН, КПП, адрес и основной ОКВЭД; ФИО и
  должность руководителя предлагаются как сведения о подписанте.
- ЕГРИП переносит ФИО, ИНН, ОГРНИП и основной ОКВЭД; предприниматель
  предлагается как подписант без отдельного повторного ввода.

ГРН отдельных записей и личный ИНН руководителя не переносятся в заявление:
официальный бланк товарного знака не запрашивает эти сведения. Все предложенные
поля сохраняют источник и требуют проверки пользователем.

## 4. Схема полей заявления

`backend/scripts/analyze_application_template.py` →
`resources/application_templates/trademark_application.schema.json`

Структура бланка извлекается детерминированно (pdfplumber): коды INID
ВОИС ST.9, подписи полей, таблицы, координаты чекбоксов. Схема содержит
SHA-256 исходного бланка, версию и дату анализа.

На приложенном образце: 34 поля описано и все найдены, 56 чекбоксов
с распознанными подписями, 3 таблицы, нераспознанного нет.

### Ограничение: чекбоксы

Чекбоксы бланка нарисованы **векторными прямоугольниками** 5.8×5.8 pt и
в текстовом слое отсутствуют полностью. AcroForm в файле нет.

В приложенном образце все 56 имеют `fill=False` — включая «словесный
знак», хотя описание в том же документе прямо говорит: «Заявлено словесное
обозначение «ЗВЁЗДОЧКА»». Отмеченность из PDF надёжно не определяется.

Поэтому: `state` всегда `undetermined`, `manual_confirmation_required`
всегда `true`. Это записано **внутрь схемы**, а не только в документацию.
Позиции и подписи при этом извлекаются — интерфейс показывает варианты
специалисту для ручного выбора.

Это касается вида знака, типа приоритета и пункта уплаченной пошлины.

## 5. Сопоставление полей

`resources/field_mappings/registry_to_application.yaml` (версионируется)
`app/document_processing/mappers/field_mapping.py`

Цепочка `реестр → карточка дела → заявление`:

| Из выписки | В деле | В заявлении |
|---|---|---|
| `registry.legal_entity.full_name` | `case.applicant.full_name` | `application.applicant.name` |
| `registry.legal_entity.inn` | `case.applicant.inn` | `application.applicant.inn` |
| `registry.legal_entity.ogrn` | `case.applicant.ogrn` | `application.applicant.ogrn` |
| `registry.legal_entity.address.full` | `case.applicant.legal_address` | `application.applicant.address` |

Правила:

- расхождение выписки и карточки дела → `conflict`;
- обязательное поле нельзя «оставить пустым»;
- у ненайденного значения недоступно «принять»;
- **решение специалиста окончательно** и не пересчитывается автоматикой;
- поля заявления без источника в выписке перечислены явно
  (`not_sourced_from_registry`), чтобы отсутствие источника было видно.

Пока хотя бы одно критичное обязательное поле в статусе
`missing`/`conflict`/`needs_review`, сводка возвращает
`can_generate_draft: false` — черновик заявления не формируется.

## 6. Политика LLM

LLM **не участвует** в извлечении реквизитов из реестровых выписок.

Допустим только как fallback, когда текст извлечён, но правила не нашли
обязательное поле, либо по явному запросу пользователя («повторный
AI-анализ»). При этом: передаётся минимальный фрагмент, а не весь
документ; результат никогда не считается подтверждённым.

Параметр `use_llm` в `/intake/parse-application` по умолчанию **выключен**.

### Известное ограничение существующего парсера заявок

`app/agents/intake/application_pdf_parser.py` (парсер бланка по INID-кодам)
на приложенном образце извлекает верно наименование, ИНН, ОГРН, КПП, класс
МКТУ и перечень товаров, но ошибается в четырёх местах:

- в качестве обозначения подхватывает подпись поля, а не значение;
- вид знака определяет как «изобразительный» (на деле словесный) —
  это следствие нечитаемых чекбоксов;
- в поле представителя попадает служебный текст;
- в «номер международной регистрации» попадает **личный ИНН плательщика**;
- `confidence` — зашитые константы, а не измеренная уверенность.

Этот парсер к контуру ЕГРЮЛ отношения не имеет и переработан не был.
Задача вынесена в `docs/roadmap.md` (P1).

## 7. Метрики

`POST /source-documents/{id}/extract` возвращает:

```json
{
  "fields_extracted": 21,
  "preserved_confirmed_fields": 2,
  "by_status": {"matched": 21},
  "extraction_method": "regex",
  "llm_used": false
}
```

Повторный запуск извлечения **сохраняет** уже подтверждённые специалистом
поля — его работа не теряется.

## 8. Персональные данные

- ФИО руководителя помечены `is_sensitive`, в интерфейсе скрыты по умолчанию.
- Персональные данные учредителей **не извлекаются**: задаче они не нужны.
- В аудите значения чувствительных полей маскируются.
- В логах маскируются ИНН физлица, СНИЛС, паспорт, локальная часть email,
  пароли и токены. Публичные реквизиты (ИНН юрлица, ОГРН) сохраняются.
- Обезличенные фикстуры в тестах: реквизиты из приложенных документов
  в тесты не копируются.
