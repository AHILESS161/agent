## 1. LLM

`app/infrastructure/llm/` · настройка через `LLM_PROVIDER`, `LLM_BASE_URL`,
`LLM_API_KEY`, `LLM_MODEL`.

| Значение | Поведение |
|---|---|
| `mock` | детерминированные ответы, без сети |
| `gigachat` | OAuth по Authorization Key и GigaChat API |
| `openai` / `local` | OpenAI-совместимый HTTP API |

Промпты вынесены в YAML-реестр `backend/prompts/` с версионированием.

Для GigaChat используется общий клиент на процесс: OAuth-токен повторно
используется до истечения, вызовы сериализуются и выполняются с минимальным
интервалом. Временные ответы `429` и `5xx` повторяются до пяти раз с
экспоненциальной задержкой и учётом `Retry-After`. Обрезанный структурированный
ответ определяется по `finish_reason` и ошибке JSON, а не принимается за вывод.
Параметры: `GIGACHAT_MIN_REQUEST_INTERVAL` и `GIGACHAT_MAX_RETRIES`.

**LLM не участвует** в извлечении реквизитов из реестровых выписок —
там только regex и правила. Политика применения: `docs/document-extraction.md`, §6.

## 2. Реестр товарных знаков

`app/infrastructure/providers/base.py` — контракт
`TrademarkRegistryProvider`.

Настройка: `FIPS_PROVIDER`.

| Значение | Поведение |
|---|---|
| `mock` | демо-датасет, 55 записей, fuzzy + фонетика |
| `rospatent_public` | анонимный read-only поиск регистраций и заявок через публичную поисковую платформу; режим `limited` |
| `fips` / `rospatent` | официальный bearer API поисковой платформы; режим `real` |

Рабочий локальный профиль использует `rospatent_public`. Он не требует
API-ключа, но опирается на недокументированный протокол публичной страницы,
поэтому не считается полным официальным поиском. Молчаливая подмена режимов
запрещена: в оценке и отчёте всегда сохраняется `real`, `limited` либо `demo`.

### Участие реестра в анализе

`run_conflict_search` выполняет поиск по исходному обозначению,
транслитерации и допустимым переводам. Сначала проверяются регистрации и заявки
в выбранных классах МКТУ, после этого выполняется ограниченный контрольный
поиск без классов. После дедупликации система:

1. детерминированно рассчитывает графическое, фонетическое, смысловое сходство
   и однородность классов;
2. при неоднозначном межъязыковом совпадении обращается к LLM за смысловой
   проверкой пары обозначений;
3. до порогового отсечения передаёт в один LLM-review до 6 приоритетных
   карточек реестра; если структурированный ответ обрезан, повторяет проверку
   для 3 наиболее рискованных карточек;
4. модель применяет пункты 40–45 Правил № 482 и пункт 162 Постановления
   Пленума ВС РФ № 10: проверяет статус/приоритет, общее впечатление, сильные
   и слабые элементы, однородность товаров, аргументы и контраргументы;
5. сохраняет комментарий модели вместе с исходными `record_id` и результатами
   расчёта в аудите оценки.

В пакетный LLM-контекст входят: тип источника (`registration` или
`application`), обозначение, владелец, классы МКТУ, статус, даты, номера
заявки и регистрации и рассчитанные коэффициенты. Модель объясняет факторы
риска, но не может менять коэффициенты или создавать новые карточки:
неизвестные `record_id` отбрасываются. Обоснованный вывод `medium`, `high` или
`critical` может поднять допороговую карточку на ручную проверку, но только при
независимой опоре на выбранные классы либо заметное сходство обозначений.

### Нормализованная модель результата

Определена в `providers/base.py`: номер, статус, дата приоритета, дата
регистрации, правообладатель, классы МКТУ, товары/услуги, обозначение,
источник, ссылка.

### Что требуется для промышленного официального режима

1. Легальный доступ к данным (API-ключ либо соглашение).
2. Договорный доступ и проверка набора данных официального провайдера.
3. Явная передача режима поиска (`real` / `demo` / `limited`) в отчёт.
4. Тесты на недоступность источника и частичные результаты.

## 3. Inbound router — проект, не реализовано

Единая точка приёма событий из CRM, почты, webhook и ручной загрузки.
Сейчас работает только ручная загрузка через интерфейс.

### Нормализованное событие

```
source                  crm | email | manual_upload | webhook | api
external_event_id       идентификатор в системе-источнике
received_at
sender
subject
text
metadata
attachments
links
target_case_id          если дело известно
raw_payload_reference   ссылка на сохранённый исходный payload
idempotency_key
```

### Требования

- Повторная доставка события **не создаёт дубликат** — по `idempotency_key`.
- Исходный payload сохраняется и связывается с аудитом.
- Файлы, текст и ссылки попадают в общий пайплайн обработки документов.
- Событие либо создаёт дело-черновик, либо привязывается к существующему.
- Для webhook — проверка подписи при наличии секрета.

### Задел в текущем коде

Модель `SourceDocument` уже содержит поле `source_channel`
(`manual_upload` / `crm` / `email` / `webhook` / `api`). Документы,
пришедшие из внешних источников, будут отличимы без миграции схемы.

Модели `InboundEvent` пока нет.

### Планируемые адаптеры

| Интерфейс | Назначение |
|---|---|
| `CRMAdapter` | получение сделок и вложений |
| `EmailAdapter` | приём письма: отправитель, тема, текст, вложения |
| `RospatentAdapter` | поиск по реестру (частично есть как провайдер) |

Для демо достаточно локального mock-адаптера почты и тестового
webhook-эндпоинта с проверкой подписи.

## 4. Файловое хранилище

`app/services/file_storage.py` — локальный каталог, адресация по SHA-256.

Интерфейс намеренно узкий: `save_upload` / `read_file` / `delete_file` /
`check_storage`. Замена на S3/MinIO не затронет вызывающий код.

Настройка: `FILE_STORAGE_PATH`, `MAX_UPLOAD_MB`.

---

## 5. Что запрещено в демо-режиме

При `DEMO_MODE=true` система не выполняет реальных внешних действий:
не подаёт заявку, не отправляет письма, не изменяет данные во внешних
системах. Подача дополнительно защищена флагом `ENABLE_REAL_SUBMISSION`
и требованием явного подтверждения специалистом.
