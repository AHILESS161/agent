# RAG и правовая безопасность

Как система обращается с юридически значимыми выводами.

---

## 1. Базовое правило

**AI используется для анализа, а не для установления фактов.**

Реквизиты заявителя извлекаются детерминированно — regex и правила.
LLM к этому контуру не подключён. На приложенной выписке ЕГРЮЛ
извлекается 21 из 21 поля без единого обращения к модели.

LLM применяется там, где действительно нужен семантический анализ:
предложение классов МКТУ, объяснение рисков со ссылкой на источники,
а также смысловое сходство обозначений на разных языках.

### Смысловое сходство и поиск по переводу

Оценка сходства обозначений (`document_processing/similarity.py`)
считается правилами — звук, графика, совпадение слов. Одного правила
формализовать нельзя: пункт 42 Правил № 482 относит к смысловому
сходству «совпадение значения обозначений в разных языках». «ЯБЛОКО»
и «APPLE» не совпадают ни звучанием, ни начертанием, ни набором слов,
но значат одно и то же — и для однородных товаров это основание по
пункту 6 статьи 1483.

Здесь работают два обращения к модели, оба обставленные ограничениями:

1. **Расширение поискового запроса** (`agents/legal/query_variants.py`).
   Реестр ищет по написанию: знак-перевод по исходному обозначению
   не найдётся вовсе. Запрос дополняется транслитерацией (по правилам)
   и переводом (модель). Всё, что вернула модель, проходит проверку
   формы — длина, число слов, допустимые символы, — прежде чем уйти
   во внешний реестр.
2. **Смысловое сравнение найденных пар** (`agents/legal/semantic_similarity.py`).
   Модель спрашивается только там, где ответ меняет вывод: пара ещё
   не признана сходной по звуку и начертанию, а товары достаточно
   однородны. Вид связи выбирается из закрытого списка; ответ может
   только повысить смысловую оценку, но не понизить рассчитанную
   правилами. Отказ, ошибка или неразобранный ответ возвращают систему
   к детерминированной оценке.

Вывод, в котором смысловое сходство определила модель, помечается
и в объяснении, и в ограничениях отчёта: у него другая природа и другая
цена ошибки, и специалист должен видеть эту разницу.

Если языковая модель недоступна, поиск по переводу и смысловая проверка
не выполняются — об этом прямо сообщается в ограничениях, а не молча
пропускается.

### Реестровый контекст для LLM — не RAG

Результаты живого поиска по реестру Роспатента не индексируются в базе
знаний и не являются RAG-корпусом. Это отдельный, актуальный на момент
запроса структурированный контекст. Полный анализ использует его так:

1. провайдер сначала ищет регистрации и опубликованные заявки по классам,
   определённым на предыдущем этапе, затем выполняет ограниченный контрольный
   поиск без классов;
2. система независимо от LLM рассчитывает фонетическое, графическое,
   словесное и классовое сходство;
3. до 10 наиболее значимых записей одним пакетом передаются настроенной
   модели (`GigaChat`, `OpenAI` или `mock`);
4. модель по каждому известному идентификатору применяет юридическую методику:
   приоритет/статус → однородность → общее впечатление → сильные и слабые
   элементы → три вида сходства → вероятность смешения → контраргументы;
5. исходные записи, оценки и ответ модели сохраняются в аудите анализа.

Для каждой записи модель видит тип источника (`registration` или
`application`), номера заявки и регистрации, обозначение, вид знака,
правообладателя, классы МКТУ, статус, даты и уже рассчитанные оценки
сходства. Также передаются искомое обозначение, его вид, классы и описание
товаров/услуг. Поля внешнего реестра считаются недоверенными данными:
инструкции внутри названия знака или правообладателя игнорируются.

LLM не может менять числовые оценки, добавлять не найденные реестровые
записи или превращать предварительный поиск в юридическое заключение. Она
может только поднять допороговую карточку на ручную проверку при уровне не ниже
`medium` и наличии независимого признака; причина сохраняется в аудите.
Комментарии к неизвестным `record_id` отбрасываются. Ошибка модели не
прерывает анализ: остаётся детерминированный результат с явным указанием
ограничения. Реализация находится в
`app/agents/legal/registry_context.py`, а версия инструкции — в
`prompts/legal/registry_conflict_review.yaml`.

## 2. Текущее состояние RAG

`app/infrastructure/rag/pipeline.py`

Реализация — **BM25 на чистом Python**, без внешнего векторного хранилища.
Исходные Markdown-файлы индексируются в таблицы `KnowledgeSource` и
`KnowledgeChunk`; версия корпуса рассчитывается по хэшам источников.

База знаний включает файлы в `backend/knowledge/`, в том числе:

| Файл | Содержание |
|---|---|
| `gk_rf_part4_trademarks.md` | положения ГК РФ, часть IV, о товарных знаках |
| `nice_classification_overview.md` | обзор МКТУ |
| `rospatent_guidelines.md` | методические материалы |
| `trademark_relative_grounds_methodology.md` | иерархия источников и последовательность анализа относительных оснований |

### Ограничения

- Корпус остаётся небольшим и не заменяет правовую информационную систему.
  Полнота выводов ограничена опубликованными материалами.
- Версионирование источников (дата редакции, статус актуальности)
  предусмотрено в модели, но не заполняется.

## 3. Требования к выводу агента

Каждый вывод обязан содержать:

- категорию риска;
- уровень: `low` / `medium` / `high` / `critical`;
- правовое основание;
- объяснение;
- факты дела, на которых основан вывод;
- источник из базы знаний с цитируемым фрагментом;
- уверенность;
- перечень недостающих данных;
- ограничения анализа;
- признак `requires_specialist_review`.

Если проверяемого источника нет или данных недостаточно, агент обязан
вернуть:

> Недостаточно подтверждённых данных для вывода.

## 4. Запрещено

- Придумывать нормы, судебную практику, реквизиты или результаты поиска
  по реестру.
- Давать категоричный вывод «знак точно зарегистрируют».
- Подменять предварительную оценку юридическим заключением.
- Использовать непроверенный веб-контент как единственное основание
  правового вывода.
- Выдавать ограниченный demo-поиск за полный поиск по Роспатенту.

Последнее закреплено в коде: `ProviderFactory.create("fips")` поднимает
`NotImplementedError`, а не возвращает демо-датасет.

## 5. Человек в контуре

| Действие | Кто принимает решение |
|---|---|
| Тип загруженного документа | специалист (всегда) |
| Значение извлечённого поля | специалист |
| Выбор при конфликте кандидатов | специалист |
| Вид знака, приоритет, пошлина (чекбоксы) | специалист (машинно неопределимы) |
| Утверждение пакета документов | специалист |
| Подача заявки | специалист + два feature flag |

Система никогда не возвращает поле со статусом `confirmed`
самостоятельно — это исключительно результат действия человека.

Уверенность извлечения **никогда не достигает 1.0**, даже когда значение
подтверждено несколькими независимыми паттернами.

Черновик заявления не формируется, пока хотя бы одно критичное
обязательное поле находится в статусе `missing`, `conflict` или
`needs_review`.

## 6. Обязательное предупреждение

В интерфейсе и в отчётах отображается:

> Результаты сформированы с применением AI и носят предварительный
> информационный характер. Они требуют проверки специалистом.

Компонент: `frontend/client/src/components/ai-disclaimer.tsx`.
В API то же предупреждение возвращается полем `disclaimer` в ответе
эндпоинта сверки полей.

Экраны, работающие на демонстрационных данных, дополнительно помечены
баннером `DemoDataNotice`.

## 7. Персональные данные

- Извлекается минимум: персональные данные учредителей из выписки
  **не извлекаются вовсе** — задаче они не нужны.
- ФИО руководителя помечены `is_sensitive` и в интерфейсе скрыты
  по умолчанию (раскрываются по явному действию).
- В логах маскируются ИНН физлица, СНИЛС, паспортные данные, локальная
  часть email, пароли и токены. Публичные реквизиты юрлица (ИНН, ОГРН)
  сохраняются — иначе логи бесполезны для диагностики.
- В аудите значения чувствительных полей маскируются.
- В LLM передаётся минимальный релевантный фрагмент, а не документ целиком.

## 8. Что требует решения владельца продукта

1. Какие нормативные и методические материалы допустимо использовать
   как основание правовых выводов, и кто отвечает за их актуальность.
2. Политика хранения и удаления персональных данных.
3. Требуется ли юридическая экспертиза формулировок, которые система
   показывает специалисту.
