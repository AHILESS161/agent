## Развёртывание

1. Перед обновлением сохранить прежний образ, ревизию и согласованный бэкап.
2. Задать отдельный случайный `SECRET_KEY` (например, `openssl rand -hex 32`).
   `ENVIRONMENT=production` задаётся Compose принудительно. Шаблонный ключ и DEBUG
   останавливают запуск; ошибки конфигурации не печатают значения входа.
3. Подготовить `/etc/registr-backup.env` с правами `600`: `RESTIC_REPOSITORY`,
   `RESTIC_PASSWORD_FILE`, необходимые учётные данные внешнего хранилища.
   Хранилище выбирает владелец проекта; секреты не сохраняются в репозитории.
4. Инициализировать restic-репозиторий, запустить `bash deploy/backup.sh`.
   Ожидать комплект `backups/backup-*` с `SHA256SUMS` и `OFFSITE_OK`.
5. Запустить `bash deploy/restore-check.sh /absolute/path/to/backup-*`.
   Скрипт поднимает отдельный временный PostgreSQL, восстанавливает dump и
   сверяет SHA-256 каждого документа. Рабочая БД не изменяется.
6. После приёмки изменений выполнить `bash deploy/deploy.sh`. Скрипт проверяет
   `/ready` через API и публичный прокси; `/healthz` — только liveness nginx.
7. Установить `deploy/registr-backup.service` и `.timer` в `/etc/systemd/system`,
   затем `systemctl daemon-reload` и `systemctl enable --now registr-backup.timer`.
   Проверять результат через `systemctl status registr-backup.service`.

Бэкап кратковременно останавливает API и worker, но автоматически запускает
ранее работавшие сервисы и при ошибке. Для круглосуточного сервиса в дальнейшем
потребуется backup без окна обслуживания. RPO при ежедневном расписании — до
24 часов; фактический RTO измеряет restore-check и подтверждает оператор.
Внешнюю копию тоже следует периодически восстанавливать через restic restore
в отдельный каталог и проверять этим же скриптом.

`BACKUP_LOCAL_ONLY=true` предназначен для изолированного CI/локальной проверки:
он явно не подтверждает наличие внешней копии. Локальные комплекты автоматически
не удаляются, пока не подтверждена политика хранения. Следить за заполнением диска.

## Лимиты и обслуживание

Начальные лимиты: 100 заявок, 200 документов / 250 МБ на пользователя;
2 активных задания пользователя, 20 суммарно. LLM резервирует дневной бюджет
в общей БД до каждого запроса, включая повторы: размер JSON в UTF-8 плюс верхний
лимит ответа. Это консервативные единицы расхода, а не сумма в рублях; лимиты
по умолчанию — 2 млн на пользователя и 10 млн на стенд, сброс по UTC.
Одновременно допускается один запрос LLM на процесс (API и worker раздельно).

На 3 ГБ VPS заданы максимумы: PostgreSQL 512 МБ, API 1152 МБ (включая парсер),
worker 640 МБ, nginx 96 МБ, Caddy 128 МБ. Это потолки, а не резервы; отдельная
нагрузочная проверка нужна перед расширением использования. При нехватке 512 МБ
диска загрузки отклоняются, `/ready` становится неготовым. Логи — 3 × 10 МБ
на контейнер. Внешний мониторинг должен проверять именно `/ready`.

Физический GC: `bash deploy/maintenance.sh`, по умолчанию хранит сироты 7 дней.
Запускается только с остановленными API/worker под общей maintenance-блокировкой;
повторно сверяет ссылки в БД. Прямой запуск GC при работающих писателях запрещён.

Старые bcrypt-пароли до 72 байт обновляются при успешном входе. Для ранее
обрезавшихся паролей длиннее 72 байт нужен административный сброс: угадывать
отброшенный суффикс нельзя. После смены пароля интерфейс предлагает повторный вход.
Общий `/transition` теперь требует `expected_status`; результаты обработки
выставляют профильные операции, а не произвольный запрос смены статуса.

## Обновление зависимостей

```sh
uv pip compile backend/requirements.txt --python-version 3.12 --python-platform linux --generate-hashes -o backend/requirements.lock
uv pip compile backend/requirements-dev.txt -c backend/requirements.lock --python-version 3.12 --python-platform linux --generate-hashes -o backend/requirements-dev.lock
```

Обновление lock-файлов и digest образа проходит тот же CI. Аудит пакетов не
заменяет инвентаризацию и сканирование реально развёрнутого образа на сервере.
